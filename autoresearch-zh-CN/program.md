# autoresearch

[English 原文](program.en.md) · [项目说明](README.md) · [中文学习教程](docs/学习教程.md)

这是一个让大语言模型自主开展研究的实验。下面是原有实验协议的中文翻译；教程中的练习和本文件规定的持续自动实验是不同的学习阶段。

**目录约定：**本中文版位于同一仓库的 `autoresearch-zh-CN/` 子目录。以下文件路径和训练命令以该目录为工作目录；Git 分支、提交和重置操作作用于整个 `aL0ng-z/autoresearch` 仓库，实验代码路径为 `autoresearch-zh-CN/train.py`。

## 初始化设置

启动一轮新实验时，与用户共同完成以下准备：

1. **确定本轮标签**：根据当天日期提出一个标签，例如 `mar5`。分支 `autoresearch/<tag>` 必须尚不存在，因为这是一次全新的实验运行。
2. **创建分支**：从当前 `master` 创建分支：`git checkout -b autoresearch/<tag>`。
3. **阅读范围内的文件**：仓库很小，完整阅读以下文件以了解上下文：
   - `README.md`：仓库背景。
   - `prepare.py`：固定常量、数据准备、分词器、数据加载器和评估函数。不要修改。
   - `train.py`：你要修改的文件，包括模型架构、优化器和训练循环。
4. **确认数据存在**：检查 `~/.cache/autoresearch/` 中是否包含数据分片和分词器。如果没有，告知用户运行 `uv run prepare.py`。
5. **初始化 `results.tsv`**：创建仅含表头的 `results.tsv`。第一次运行完成后再记录基线结果。
6. **确认后开始**：确认准备工作已经就绪。

得到确认后，开始实验。

## 实验规则

每个实验使用一张 GPU。训练脚本具有**固定 5 分钟的时间预算**，按实际训练耗时计时，不包括启动和编译。启动命令是：`uv run train.py`。

**允许的操作：**

- 修改 `train.py`。这是唯一允许编辑的文件；模型架构、优化器、超参数、训练循环、批大小、模型规模等均可调整。

**不允许的操作：**

- 修改 `prepare.py`。该文件是只读的，包含固定评估逻辑、数据加载、分词器以及时间预算、序列长度等训练常量。
- 安装新包或增加依赖。只能使用 `pyproject.toml` 中已有的依赖。
- 修改评估机制。`prepare.py` 中的 `evaluate_bpb` 函数是权威评估标准。

**目标很简单：让 `val_bpb` 尽可能低。** 时间预算固定，因此不需要把训练时长另设为优化目标；训练预算始终是 5 分钟。你可以改变架构、优化器、超参数、批大小和模型规模。约束是代码能够运行、不崩溃，并遵守时间预算。

**显存是软约束。** 如果能显著改善 `val_bpb`，适度增加显存占用可以接受，但不能急剧膨胀。

**简洁性标准：**其他条件相同时，越简单越好。为微小改进引入难看的复杂代码不值得；反过来，删除代码后取得相同或更好的结果，就是很好的简化收益。决定是否保留改动时，要权衡复杂度成本和改善幅度。例如：为了降低 0.001 的 `val_bpb`，增加 20 行杂乱的补丁代码，大概不值得；通过删除代码降低 0.001，则应该保留；改善约为 0，但代码明显更简单，也可以保留。

**第一次运行：**始终先建立基线，因此第一次应原样运行训练脚本。

## 输出格式

脚本完成后，会输出类似下面的汇总：

```text
---
val_bpb:          0.997900
training_seconds: 300.1
total_seconds:    325.9
peak_vram_mb:     45060.2
mfu_percent:      39.80
total_tokens_M:   499.6
num_steps:        953
num_params_M:     50.3
depth:            8
```

以上为原文示例数据，不是当前机器的实测结果。脚本按照 5 分钟训练预算停止，因此不同计算平台上的其他统计数值可能不同。可以从日志提取核心指标：

```bash
grep "^val_bpb:" run.log
```

> **译注：**完整进程还包含启动、编译和评估等开销，实际计时细节见[教程第 8 节](docs/学习教程.md#training)。Windows PowerShell 的日志查看命令也在教程中给出。

## 记录结果

每个实验完成后，将结果写入 `results.tsv`。使用制表符分隔，**不要使用逗号分隔**，因为描述文字中可能包含逗号。

TSV 文件含一行表头和五列。以下示意中的 `\t` 表示一个真实制表符：

```text
commit\tval_bpb\tmemory_gb\tstatus\tdescription
```

1. Git 提交哈希：短格式，7 个字符。
2. 本次得到的 `val_bpb`，例如 `1.234567`；崩溃时填写 `0.000000`。
3. 峰值显存，按 GB 记录并保留一位小数，例如 `12.3`，计算方式为 `peak_vram_mb / 1024`；崩溃时填写 `0.0`。
4. 状态：`keep`（保留）、`discard`（放弃）或 `crash`（崩溃）。
5. 对本次尝试的简短描述。

示例：

```text
commit\tval_bpb\tmemory_gb\tstatus\tdescription
a1b2c3d\t0.997900\t44.0\tkeep\t基线
b2c3d4e\t0.993200\t44.2\tkeep\t将学习率提高到 0.04
c3d4e5f\t1.005000\t44.0\tdiscard\t将激活函数改为 GeLU
d4e5f6g\t0.000000\t0.0\tcrash\t模型宽度翻倍，显存不足
```

示例哈希仅作占位。`results.tsv` 中的字段名和状态值必须保持英文，供分析 Notebook 读取。

## 实验循环

所有实验在专用分支上进行，例如 `autoresearch/mar5` 或 `autoresearch/mar5-gpu0`。

持续重复以下流程：

1. 查看 Git 状态，确认当前分支和提交。
2. 根据一个实验想法，直接修改 `train.py`。
3. 创建 Git 提交。
4. 运行实验：`uv run train.py > run.log 2>&1`。重定向所有输出，不要使用 `tee`，也不要让输出大量占用上下文。
5. 读取结果：`grep "^val_bpb:\|^peak_vram_mb:" run.log`。
6. 如果没有提取到指标，则按运行失败处理。用 `tail -n 50 run.log` 查看 Python 异常堆栈并尝试修复。如果尝试多次仍无法正常运行，就放弃这次方案。
7. 将结果记录到 TSV 文件。**不要提交 `results.tsv`，让它保持不被 Git 跟踪。**
8. 如果 `val_bpb` 改善，即数值更低，则保留该提交，让分支继续前进。
9. 如果 `val_bpb` 相同或更差，则将 Git 状态重置回本次实验开始时的位置。

这里的设想是：你是一个完全自主的研究者，不断尝试新想法。有效就保留，无效就放弃，通过推进分支持续迭代。遇到瓶颈时可以回退更早的状态，但应该极少这样做，甚至尽量避免。

**超时：**原文预期每次实验约 5 分钟，再加少量启动和评估开销。如果某次运行超过 10 分钟，则终止该进程，按失败处理，放弃改动并回退。

**崩溃：**如果运行因显存不足（OOM）、程序错误等原因崩溃，请自行判断：如果是拼写错误、漏掉导入之类容易修复的小问题，就修复后重试；如果想法本身存在根本问题，则跳过，在 TSV 中记录 `crash`，继续下一次实验。

**持续运行：**实验循环一旦开始，即初始设置完成之后，就不要停下来询问用户是否继续，也不要问“还要继续吗”或“现在适合停止吗”。用户可能正在睡觉或已经离开电脑，期望你持续工作，直到手动停止。你应自主推进；没有想法时，继续思考，阅读代码提到的论文，重读相关文件，组合此前接近成功的改动，或者尝试更大幅度的架构变化。循环一直运行到用户中断为止。

一种典型使用场景是：用户睡觉时让实验持续运行。按每次约 5 分钟估算，每小时约 12 次，睡一晚约能完成 100 次；醒来即可查看已经完成的实验结果。实际数量取决于运行和决策开销。

> **译注：**上面的循环步骤默认“同分则放弃”；前文的简洁性标准允许“同分但明显更简单”作为例外。制定自己的实验协议时，应明确这个例外的判断依据。
