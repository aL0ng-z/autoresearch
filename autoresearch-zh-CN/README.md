> 曾几何时，前沿 AI 研究还是由“肉体计算机”完成的。他们在吃饭、睡觉和其他娱乐活动的间隙开展研究，偶尔通过声波互连，在一种叫“组会”的仪式中同步信息。那个时代早已过去。如今，研究完全属于自主运行的 AI 智能体群，它们遍布天空中庞大的计算集群。智能体声称，我们已经迭代到了第 10,205 代代码库；但无论如何，也没人能判断这个说法是真是假，因为所谓的“代码”已经变成了能够自我修改、超出人类理解范围的二进制程序。这个仓库讲述的，就是这一切如何开始。
>
> —— @karpathy，2026 年 3 月

这个项目的想法是：给 AI 智能体一套规模小、但真实可用的大语言模型（LLM）训练环境，让它整夜自主实验。它修改代码，训练 5 分钟，检查结果是否改善，决定保留还是放弃改动，然后重复这个过程。第二天早晨，你会看到一份实验记录，以及一个有望变得更好的模型。这里的训练代码是 [nanochat](https://github.com/karpathy/nanochat) 的简化单 GPU 实现。

核心思路是：你不再像传统研究者那样直接修改 Python 文件，而是编写 `program.md` 这样的 Markdown 文件，为 AI 智能体提供上下文，并组织你的自主研究工作。仓库默认的 `program.md` 刻意保持为一个极简基线。你可以逐步改进它，寻找能让研究进展更快的“研究组织代码”，也可以加入更多智能体。项目的更多背景见作者的[这条推文](https://x.com/karpathy/status/2029701092347630069)和[这条推文](https://x.com/karpathy/status/2031135152349524125)。

## 工作原理

仓库刻意保持精简，真正关键的只有三个文件：

- **`prepare.py`**：固定常量、一次性数据准备（下载训练数据、训练 BPE 分词器），以及运行时工具（数据加载器、评估函数）。标准实验中不修改这个文件。
- **`train.py`**：智能体唯一需要编辑的文件。包含完整 GPT 模型、优化器（Muon + AdamW）和训练循环。模型架构、超参数、优化器、批大小等都可以调整。**由智能体修改并迭代。**
- **`program.md`**：面向一个智能体的基础指令。让智能体阅读它，即可按其中的流程开展工作。**由人类修改并迭代。**

按照设计，每次训练使用**固定 5 分钟的时间预算**，按实际经过的训练时间计时，不计启动和编译开销。评估指标是 **`val_bpb`**，即验证集上的每字节比特数（validation bits per byte）：越低越好。它按字节归一化，避免直接以 token 为单位的损失受到词表大小的影响，便于比较模型改动。

如果你刚开始学习神经网络，原作者还推荐了这份[入门指南](https://x.com/hooeem/status/2030720614752039185)。本地也提供了面向“会 Python、希望学习 Transformer 与自动实验”的[中文学习教程](docs/学习教程.md)。

> **译注：**“5 分钟”是训练预算的简写，不是整个进程的严格总时长。当前代码跳过最初 11 次参数更新的计时，再累计训练步骤耗时，并在完成一个步骤后检查是否达到 300 秒；启动、编译和最终评估还会增加运行时间。详见教程第 8 节。

## 快速开始

**要求：**一张 NVIDIA GPU（原作者在 H100 上测试）、Python 3.10 或更高版本，以及 [uv](https://docs.astral.sh/uv/)。

下面保留原文的 Bash 命令，适用于相应的 Linux／类 Unix Shell；Windows 的环境说明见[教程第 3 节](docs/学习教程.md#environment)。

```bash
# 1. 安装 uv 项目管理工具（如果尚未安装）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 2. 安装依赖
uv sync

# 3. 下载数据并训练分词器（只需准备一次；原文估计约 2 分钟）
uv run prepare.py

# 4. 手动运行一次训练实验（约 5 分钟训练，另加其他开销）
uv run train.py
```

如果上述命令均正常完成，说明环境已经可以工作，可以进一步进入自主研究模式。下载和准备耗时取决于网络、CPU 和缓存情况。

## 设计取舍

- **只修改一个文件。** 智能体只编辑 `train.py`，让实验范围保持可控，也让代码差异容易审查。
- **固定时间预算。** 每次训练预算为 5 分钟。原文据此粗略估计每小时约 12 次实验、睡一晚约 100 次。这样做有两个优点：首先，智能体无论改变模型大小、批大小还是架构，都可以在相同训练时间预算下比较；其次，autoresearch 会寻找更适合你的计算平台及该预算的模型。代价是：不同计算平台上的实验和结果不能直接等同。实际实验频率还要计入启动、评估和智能体思考、编辑代码的时间。
- **尽量自包含。** 除 PyTorch 和少量其他包外，不引入复杂依赖；没有分布式训练，也没有复杂配置系统。一个 GPU、一个可编辑训练文件、一个核心指标。

## 平台支持

当前代码需要一张 NVIDIA GPU。原则上也可以支持 CPU、MPS 和其他平台，但这样会让代码变复杂。原作者暂时不确定是否亲自承担这项工作。有需要的人可以参考完整的上游 nanochat 仓库，那里提供了更广的平台支持及相应实现，例如 Flash Attention 3 内核的回退方案、通用设备支持、自动检测等。欢迎为其他平台创建分支或发起讨论；原作者愿意在 README 的相关分支列表中添加链接。

不少人希望在比 H100 小得多的平台上尝试 autoresearch。对于 MacBook 等设备，原作者建议优先参考下列社区分支。如果希望自行创建适合小模型的分支，可以考虑这些调整：

1. 使用信息复杂度更低的数据集，例如 [TinyStories](https://huggingface.co/datasets/karpathy/tinystories-gpt4-clean)。这些是 GPT-4 生成的短故事，内容范围更窄，小得多的模型也可能产生相对合理的结果。
2. 尝试缩小 `vocab_size`，例如从 8192 降到 4096、2048、1024；甚至直接使用 UTF-8 编码后 256 种可能字节值构成的字节级分词器。
3. 大幅降低 `prepare.py` 中的 `MAX_SEQ_LEN`，视设备情况甚至可以降到 256。降低序列长度时，可以尝试适当提高 `train.py` 中的 `DEVICE_BATCH_SIZE` 来补偿；两者的乘积是每次前向／反向传播处理的 token 数。
4. 降低 `prepare.py` 中的 `EVAL_TOKENS`，减少验证集评估的数据量。
5. `train.py` 中控制模型复杂度的主要参数是 `DEPTH`，当前默认值为 8。很多其他变量由它计算得到，可以尝试降到 4。
6. 可以尝试将 `WINDOW_PATTERN` 设为 `"L"`。`"SSSL"` 使用交替的局部注意力模式，在某些设备上可能效率不佳。
7. 大幅降低 `TOTAL_BATCH_SIZE`，同时保持为 2 的幂，例如尝试 `2**14`，约 16K token；合适的数值需要实验确认。

原作者认为这些是值得尝试的超参数。你可以把这些建议和完整源代码交给编码智能体，协助调整。

> **译注：**这一小节讨论的是为其他平台创建或适配分支。修改数据集、分词器、`MAX_SEQ_LEN` 或评估 token 数后，就改变了实验条件；这与 `program.md` 要求保持 `prepare.py` 不变的标准实验流程有所区别。
